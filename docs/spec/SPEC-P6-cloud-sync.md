## 2. 现状盘点（好消息：地基基本都在）

| 维度 | 现状 | 结论 |
|---|---|---|
| 主键 | **UUID v4，客户端发号**（`README.md:204`） | ✅ 多端生成不冲突，同步模型可以「按 id upsert」 |
| 同步五件套 | `id / owner_id / created_at / updated_at / deleted_at / dirty` 五张业务表**全都有**（`core/db/tables.dart`） | ✅ 元数据齐了 |
| 删除语义 | 全部**软删**（`deleted_at`），无物理删 | ✅ 天然墓碑（tombstone），能做删除同步 |
| `dirty` 现状 | 默认 1，**从来没有代码把它清 0**（没有任何同步逻辑） | ⚠️ 语义要先定义清楚再启用，否则「全表永远 dirty」 |
| 账本隔离 | 所有查询按 `book_id`；指纹唯一索引是 `(book_id, fingerprint)` | ✅ 可按账本粒度同步 |
| 备份 | 已有完整 JSON 备份 + 恢复（`buildBackupJson` / `restoreBackupJson`），且**已带 `settings` 白名单** | ✅ 云备份可以直接复用，不用重造 |
| 网络层 | **零**（没有 http 客户端、没有 baseUrl、没有鉴权） | ❌ 从零开始 |
| 账号 | **零** | ❌ 从零开始 |
| drift | 唯一 DB writer（不变量 #1） | ⚠️ 同步下行必须走 Repository，不能在同步服务里裸写 SQL |

## 3. 架构选型

### 3.1 后端（三选一）

| 方案 | 组成 | 成本 | 上手 | 风险 |
|---|---|---|---|---|
| **A · 自建薄后端**（推荐起步） | Cloudflare Workers + D1（SQLite）+ R2（备份文件） | 免费额度足够个人项目；上量后 ~$5/月起 | 中：Dart 侧只需 HTTP + JWT | 单人维护，但代码量小（估 600–900 行） |
| B · Supabase | Postgres + Auth + Storage + RLS | 免费额度够；Pro $25/月 | 低：Auth/RLS 开箱 | 供应商锁定；国内访问延迟/可用性差 |
| C · 自建服务器（Spring Boot / Node + VPS） | 全套自己来 | VPS ¥30–60/月起 + 运维 | 高 | 运维、备案、可用性全自己扛 |

**推荐 A**：这个 App 的同步模型很轻（按行 upsert + 拉增量），不需要关系型花活；
Workers+D1 的免费额度对个人用户量足够，代码量小到一个人能维护。
**国内可用性**是硬指标 —— Supabase/Cloudflare 在国内都不稳，这一点可能需要**自建 VPS + 国内可用域名**，
即方案 C。这个选择直接决定工作量，见 §8 待拍板 ①。

### 3.2 账号（三选一）

| 方案 | 体验 | 成本 / 风险 |
|---|---|---|
| **A · 邮箱 + 验证码**（推荐） | 无密码，收码即登录 | 需要发信服务（Resend/SES，免费额度够）；国内邮箱到达率需实测 |
| B · 手机号 + 验证码 | 国内最顺 | **短信按条计费**（¥0.03–0.05/条），要实名、要签名报备 |
| C · 第三方登录（微信/Apple） | 最省事 | 需要开放平台资质、审核周期，且微信登录对个人开发者门槛高 |

**推荐 A 起步**，手机号作为 P6.4 之后再评估的增强。

## 4. 同步模型（第一版）

**原则：本机 SQLite 是主副本，云端是「多端汇合点」。** 不做 CRDT，不做操作日志，只做**行级最后写入胜**。

| 项 | 规则 |
|---|---|
| 上行 | 扫 `dirty = 1` 的行 → POST 批量 upsert → 成功后 `dirty = 0` 并记 `synced_at` |
| 下行 | `GET /changes?since=<server_seq>` 拉增量 → 按 id upsert 进本机（走 Repository，不裸写） |
| 冲突 | 同行两边都改：比 `updated_at`，**大的赢**；相等时以服务端为准（幂等） |
| 删除 | 软删行也是普通行（`deleted_at` 非空），照样上行/下行；服务端保留 90 天后物理清理 |
| 账本粒度 | 按 `book_id` 同步；新建账本先上账本行，再上它下面的数据 |
| 预算 | 唯一键 `(book_id, period)`，服务端按这个键 upsert，避免重复行 |
| 指纹 | `(book_id, fingerprint)` 唯一索引两端都成立，**同一笔不会因为同步变两条** |
| 设置（`schema_meta`） | **只同步白名单键**（`dashboard_config` / `theme_seed` / `theme_mode`，与备份同一份清单）；`active_book_id` / `autobook_*` / `onboarding_done` 永不同步 |
| 触发时机 | 冷启动、前台切回、写完一笔 5 秒防抖、手动「立即同步」 |
| 失败 | 指数退避重试；连续失败在设置页显示状态（不弹窗打扰） |

**明确不做（第一版）**：多账号共享账本、实时推送（WebSocket）、字段级合并、离线编辑冲突 UI 复杂版
（第一版冲突只给一条提示：「这笔在另一台设备上也改过，已保留最新的一次」）。

## 5. 分阶段（每阶段都可独立上线、独立回滚）

| 阶段 | 内容 | 工作量 | 验收 |
|---|---|---|---|
| **P6.1 网络地基（不改业务）** | 恢复 `INTERNET`（禁明文、只允许同步域名）+ `SyncApi` 抽象 + 空实现 + 文档话术统一（§1.2）+ 「云同步」入口（占位，默认关） | **0.5–1 天** | release 包能联网但**不发任何请求**（抓包为零）；文档口径一致 |
| **P6.2 账号** | 邮箱验证码登录、token 存储与刷新、设置页账号态、注销（云端硬删） | **3–5 天** | 登录→杀进程→仍登录；注销后云端查不到该用户任何行 |
| **P6.3 云备份（低风险先上）** | 复用现有备份 JSON 上传到对象存储；换机「从云端恢复」；**只读、不双向** | **2–3 天** | 新机登录→一键恢复→数据与旧机一致（复用 `restoreBackupJson`） |
| **P6.4 账本双向同步** | `dirty` 语义启用、增量接口、LWW 冲突、tombstone、状态 UI | **2–4 周** | 两端交替记账 100 笔不重不丢；断网编辑后恢复自动补传 |
| **P6.5 可持续运营** | 订阅（免费额度 = 1 台设备 / 云端备份 30 天；订阅 = 多端 + 长期历史） | 3–5 天 + 商店结算 | 见 §7 |

**建议先做 P6.1 + P6.3**：把「换手机不丢账」这个最痛的点解决，风险最低、立刻能收费；
P6.4 才是真正的大工程（冲突、离线、幂等），放在有用户反馈之后再做。

## 6. 安全与合规

### 6.1 硬要求

- **全链路 HTTPS**，`networkSecurityConfig` 禁明文（`cleartextTrafficPermitted=false`）；
- token 存 Keystore（不落明文文件、不进日志）；
- 服务端**只存账本行 + 邮箱**，不存设备通讯录/位置/剪贴板，不做埋点；
- **注销 = 云端硬删**（含备份文件），并在设置页给「导出后再注销」的引导；
- 同步日志只记「条数 / 时间 / 错误码」，**不记金额与备注正文**。

### 6.2 可选：端到端加密

如果想让「服务器也看不到你的账」这句站得住，可以对 `note` / `amount` 做端上加密（密钥由用户口令派生）。
代价：**服务端无法做任何聚合**（以后想做「云端报表」就没戏），且丢密码 = 数据永久不可读。
**建议第一版不做**，先明确「服务器能看到账本，但我们不卖、不分析」；等有企业/高敏用户再说。

## 7. 为什么这条路能「长久运营」

本地不联网的商业模式只有「一次性买断」，而记账 App 的持续成本（适配新 Android、修 bug、客服）
是长期的。云同步之所以能撑住：

1. **可订阅**：多端同步 + 长期云备份是天然付费点，用户也认；
2. **有留存**：数据在云端就不会因为换手机流失；
3. **不靠卖数据**：订阅收入与隐私立场不冲突 —— 这比「免费 + 广告/卖数据」干净得多。

**明确不做**：广告、行为画像、把账本数据喂给第三方模型训练。

## 9. HTTP 契约（P6.2 + P6.3 第一版）

```
Base: https://<你的域名>          全站 HTTPS，禁明文
鉴权: Authorization: Bearer <access_token>
编码: application/json（备份文件 >1 MB 时用 multipart 或直接 PUT 到 R2/本地目录）
```

| 方法 | 路径 | 用途 | 请求 | 响应 |
|---|---|---|---|---|
| POST | `/v1/auth/request-code` | 发邮箱验证码 | `{"email":"a@b.com"}` | `204`（无论邮箱是否存在都 204，防枚举） |
| POST | `/v1/auth/verify` | 校验并换 token | `{"email":"a@b.com","code":"123456"}` | `{"accessToken":"...","refreshToken":"...","expiresIn":900}` |
| POST | `/v1/auth/refresh` | 续期 | `{"refreshToken":"..."}` | 同上 |
| POST | `/v1/auth/logout` | 吊销 refresh token | — | `204` |
| DELETE | `/v1/account` | **注销**：云端硬删用户与其备份 | — | `204` |
| PUT | `/v1/backups/latest` | 上传/覆盖「最新备份」 | 备份 JSON 原文字节（与导出文件**同一份**） | `{"size":123,"sha256":"...","createdAt":"..."}` |
| GET | `/v1/backups/latest` | 换机恢复时下载 | — | 备份 JSON 原文 |
| GET | `/v1/backups` | 列历史快照（第一版只留最近 N 份） | — | `[{"id":"...","size":123,"createdAt":"..."}]` |

**服务端硬要求**（写进验收）：
1. 验证码 5 分钟过期、同邮箱 60 秒内只能发一次、单日上限（防刷短信/邮件费用）；
2. 备份**按用户隔离**，任何跨用户读取返回 404（不泄露存在性）；
3. `DELETE /v1/account` 必须**物理删除**行与对象文件，而不是打标记；
4. 日志只记 `userId / 状态码 / 字节数`，**不记备份正文**；
5. 备份在服务端**加密落盘**（磁盘级或对象级均可），密钥不进代码仓库。

## 10. 明确不做（第一版）

- 多用户共享账本 / 家庭账本协作；
- 实时推送同步（WebSocket）、字段级合并、CRDT；
- 端到端加密（§6.2 的理由）；
- iOS / Web 端；
- 把现有业务仓储改造成远端优先 —— **drift 仍是唯一 DB writer**（不变量 #1 不放）。
